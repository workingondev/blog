Post-quantum cryptography is cryptography designed to run on ordinary computers while resisting attacks from both classical and quantum computers. It is not quantum communication, and it does not require quantum hardware. The change is in the mathematical problems that security depends on.

That distinction matters. Most systems will not replace their networks or processors to become post-quantum. They will replace algorithms, key formats, protocol messages, hardware assumptions, and operational procedures—often while keeping the rest of the system running.

<h2 id="the-problem">The problem</h2>

Widely deployed public-key systems rely on mathematical problems that are difficult for known classical algorithms. RSA relies on integer factorization. Elliptic-curve systems such as ECDSA rely on the elliptic-curve discrete logarithm problem.

A sufficiently capable fault-tolerant quantum computer could run Shor’s algorithm against both families. That does not mean current quantum machines can break production keys today. It means the security assumption has a known failure condition, and long-lived systems need a migration plan before that condition arrives.

Symmetric cryptography is affected differently. Grover’s algorithm provides a quadratic search speedup rather than the structural break Shor’s algorithm gives public-key systems. In practice, larger symmetric keys and hash outputs can often restore an appropriate security margin.

For an ideal search space of size $2^n$, Grover’s asymptotic query complexity is:

$$
T_{\mathrm{quantum}} = O\!\left(\sqrt{2^n}\right) = O\!\left(2^{n/2}\right)
$$

<h2 id="what-post-quantum-means">What post-quantum means</h2>

Post-quantum schemes are built from problem families for which no efficient classical or quantum attacks are currently known. The major families include lattice-based, hash-based, code-based, and multivariate constructions.

“No known efficient attack” is deliberate language. Cryptography does not prove that an attacker will never find a better algorithm. It accumulates confidence through public analysis, conservative parameters, implementation review, and time.

The engineering trade-offs also change. A replacement may have larger public keys, signatures, or ciphertexts. It may need more working memory, different randomness guarantees, or new protections against side-channel attacks. Algorithm names alone do not describe those operational costs.

<h2 id="nist-standards">The NIST standards</h2>

In 2024, NIST published its first three finalized post-quantum cryptography standards:

- **ML-KEM (FIPS 203)** is a key-encapsulation mechanism used to establish shared secrets.
- **ML-DSA (FIPS 204)** is a lattice-based digital-signature standard.
- **SLH-DSA (FIPS 205)** is a stateless hash-based digital-signature standard.

ML-KEM addresses encryption and key establishment. ML-DSA and SLH-DSA address authentication and signatures. They are not interchangeable, and a protocol may need more than one primitive to replace its current public-key design.

Standards are a starting point rather than an automatic migration. Implementations still need constant-time behavior, careful parsing, test vectors, key lifecycle policies, failure handling, and integration into real protocols.

<h2 id="migration-is-a-systems-problem">Migration is a systems problem</h2>

Cryptographic agility is the ability to change algorithms without redesigning an entire system. In practice, agility requires explicit algorithm identifiers, versioned encodings, negotiable capabilities, testable downgrade rules, and a clear boundary between cryptographic operations and application logic.

Hybrid deployments can combine a classical and a post-quantum primitive during transition. The intended benefit is that the combined construction remains secure if at least one component remains secure. But hybrid designs also increase message sizes and implementation complexity. Their composition must be specified rather than improvised.

Inventory comes before replacement. Teams need to know where keys are created, stored, copied, rotated, verified, and embedded in long-lived data. Hidden dependencies—firmware formats, certificate chains, hardware modules, recovery procedures—often determine migration time more than the algorithm implementation itself.

A protocol envelope should make the algorithm and version explicit rather than infer them from payload shape:

```ts
type SignatureAlgorithm = "ecdsa-secp256k1" | "ml-dsa-65";

type SignedEnvelope = {
  version: 1 | 2;
  algorithm: SignatureAlgorithm;
  publicKey: Uint8Array;
  signature: Uint8Array;
  payloadHash: Uint8Array;
};

function supports(envelope: SignedEnvelope): boolean {
  return envelope.version === 2 && envelope.algorithm === "ml-dsa-65";
}
```

<h2 id="blockchain-implications">Blockchain implications</h2>

Blockchains make migration unusually visible. Public keys and signatures can remain on-chain indefinitely. Verification rules are replicated across many independent implementations, and changing them may require coordination across wallets, applications, validators, and governance processes.

Signature size affects transaction bandwidth, fee markets, block capacity, state proofs, and constrained hardware. Address derivation can sometimes hide a public key until funds are spent, but that is not a universal defense: reused addresses, account-based systems, and exposed validator keys create different risk profiles.

The right design question is therefore broader than “which post-quantum signature should replace ECDSA?” A credible plan must cover account migration, dormant funds, hardware wallets, multisignature policies, protocol upgrades, replay protection, and the period when classical and post-quantum verification coexist.

Post-quantum cryptography changes primitives. Post-quantum readiness changes systems.
