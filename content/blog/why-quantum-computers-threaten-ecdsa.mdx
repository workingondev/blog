ECDSA authenticates transactions across Bitcoin, Ethereum, wallets, secure hardware, and many other systems. Its security depends on an asymmetry: multiplying a point on an elliptic curve by a secret number is efficient, while recovering that secret number from the resulting public point is believed to be infeasible on classical computers.

Quantum computation changes that asymmetry. A sufficiently capable fault-tolerant quantum computer could use Shor’s algorithm to recover the private scalar from an ECDSA public key. Once recovered, the attacker could produce signatures that verifiers cannot distinguish from those made by the legitimate key holder.

<h2 id="what-ecdsa-assumes">What ECDSA assumes</h2>

An ECDSA private key is an integer. The corresponding public key is a point obtained through scalar multiplication on a chosen elliptic curve. Security rests on the elliptic-curve discrete logarithm problem: given the curve’s generator point and the public point, find the scalar connecting them.

Known classical methods require work that grows too quickly to be practical at standard parameter sizes. Correct implementations must also protect the signing nonce. Reusing or biasing a nonce can reveal the private key without any quantum computer at all, which is why deterministic nonces and hardened signing implementations matter today.

<Note>
Quantum risk does not replace classical implementation risk. Side channels, weak randomness, nonce failures, and compromised devices remain the immediate ways keys are lost.
</Note>

<h2 id="what-shor-changes">What Shor changes</h2>

Shor’s algorithm solves discrete logarithms in polynomial time on a quantum computer. The result is structural: increasing an elliptic-curve key from one conventional size to another does not remove the underlying vulnerability in the way increasing a symmetric key size can compensate for Grover’s algorithm.

The important qualifier is hardware. Breaking a production curve requires a large error-corrected quantum computer, not merely a device with a large advertised count of noisy physical qubits. Logical qubits, gate fidelity, error correction, runtime, and the cost of a specific attack all matter.

This uncertainty affects timing, not the existence of the migration problem. Systems whose assets or authorization rules may remain valid for many years have to account for the time needed to standardize, implement, deploy, and coordinate a replacement.

<h2 id="public-key-exposure">Public-key exposure</h2>

An attacker needs the public key to run the relevant discrete-logarithm attack. Some blockchain address schemes commit to a hash of a public key and reveal the full key only when spending. That can reduce exposure for unused outputs, but it is not a complete solution.

Public keys may already be visible because an address was reused, a transaction was signed, an account model stores the key differently, or a validator and protocol key is necessarily public. Even when a key is revealed only at spend time, a future attacker might attempt to derive the private key and race a conflicting transaction if the attack becomes fast enough.

More importantly, hiding public keys does not create a migration path for ownership. A network still needs rules that let existing users authorize movement into new post-quantum accounts without giving attackers the same opportunity.

<h2 id="why-migration-is-hard">Why migration is hard</h2>

A blockchain signature scheme is connected to address formats, transaction encodings, fee calculation, hardware wallets, multisignature systems, smart contracts, light clients, and consensus verification. Larger post-quantum signatures can increase transaction weight and verification data. New algorithms also introduce different implementation and side-channel assumptions.

Coordination is the deeper problem. Users do not upgrade simultaneously. Some keys belong to dormant accounts. Some owners have lost access. Some scripts or contracts cannot express a new verification rule. A migration policy must decide how long old signatures remain valid and what happens to funds that do not move.

Aggressive deadlines can strand legitimate users. Indefinite compatibility can preserve the vulnerable path. That is a protocol-governance decision as much as a cryptographic one.

<h2 id="what-readiness-looks-like">What readiness looks like</h2>

Readiness begins with inventory: which curves are used, where public keys are exposed, which assets are long-lived, and which components are difficult to update. Protocol designers can then benchmark standardized candidates under realistic transaction and hardware constraints.

Useful preparation includes versioned address formats, explicit algorithm identifiers, upgradeable verification paths, test networks, hardware-wallet experiments, and recovery procedures. Hybrid signatures may help during transition, but they should follow a specified construction with understood security goals.

The aim is not to predict a single date for a cryptographically relevant quantum computer. It is to ensure that migration time is shorter than the warning time the system ultimately receives.
